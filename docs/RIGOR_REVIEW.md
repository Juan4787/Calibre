# Revisión de rigor — 22 de septiembre de 2026

Se corrigieron los mecanismos identificados y se conservaron pruebas de regresión. Este informe distingue esa corrección de la certificación de un producto o de contratos reales.

Base revisada: `3ede18b`. Los 12 archivos que ya estaban modificados al comenzar —11 capturas y el incidente PERF-01— se preservan. No se modifican bases de auditorías existentes. Los resultados nuevos están en `output/review-20260922/` y las trazas de navegador en `output/playwright/`; contienen únicamente datos sintéticos.

## Evidencia y comandos

Una corrida fallida o cuyo código cambió no se admite como evidencia vigente. No se recalcula un esperado económico a partir del mismo motor para demostrar su verdad: se mantienen las anclas manuales/racionales, los golden revisados y los mutantes dirigidos.

## Impacto y límites que permanecen abiertos

- **Historial:** no reescribir auditorías ni decisiones. Revisar primero corridas del motor anterior que reutilicen las mismas operaciones/conceptos en liquidaciones diferentes. Si hay asignación superpuesta, conservar originales y producir una nueva corrida; cualquier decisión económica previa requiere revisión humana. Un cambio de código exige reiniciar el servicio y el replay histórico exige el artefacto original.
  Inventario conservador de sólo lectura: `.venv/bin/python scripts/qa.py impact --db RUTA_EXISTENTE.db --feature cross_settlement`. Incluye corridas candidatas y conserva los casos de integridad desconocida para investigación; no concluye que todo candidato sea un error contractual.
- **Windows actual:** la campaña Windows conservada prueba su versión anterior. Los gates nuevos y esta versión deben ejecutarse en Windows nativo antes de afirmar portabilidad de este artefacto; Linux no lo sustituye. `platform.yml` prepara esa ejecución y exige ambas plataformas completas.
- **Volumen:** las campañas históricas de 100.000 cargos no prueban rendimiento de cada modificación ni de esta PC. No se ejecuta ese volumen localmente. La omisión de XLSX/bundle o un aborto por memoria bloquea el gate de pipeline completo. UI masiva, tiempos y memoria dependen del hardware y del dataset.
- **Cobertura causal:** las 58 familias conservan obligaciones manuales, formatos no soportados y evidencias parciales. Los tests implementados no prueban todos los layouts, toda la semántica de estilos/filas ocultas de Excel, toda degradación sostenida ni toda combinación de reglas. Un importador que acepta un libro no prueba que represente el contrato del cliente.
- **Independencia:** hashes y replay detectan alteraciones/divergencias, no una interpretación contractual falsa pero internamente consistente. Las “observaciones UI” sintéticas del inyector sólo prueban el comparador; la prueba de DOM real es el runner Chromium. Los controles de integridad no constituyen firma externa ni protección ante la reescritura coherente de todos los archivos.
- **Piloto y pago:** faltan originales, contrato validado, control documental de totales, asignaciones parciales acordadas, operación Windows del cliente, backup/restore del operador y comparación ciega. Gate P requiere esa evidencia; Gate U sigue cerrado. No hay validación comercial ni autorización de pago automático.
- **Distribución:** el lock fija las dependencias de ejecución de QA/producto, pero no promete builds bit a bit idénticos, firma de distribución ni actualización automática. Las dos deprecaciones conocidas de TestClient siguen registradas, sin tratarlas como fallos económicos.

Una familia se cierra cuando todas sus obligaciones aplicables tienen evidencia y un oráculo suficiente, no cuando desaparece una fila pendiente del documento. Para una entrega acotada de infraestructura QA, aplicar el Gate S de `RELEASE_CRITERIA.md`; su aprobación no equivale a certificar el producto completo.
